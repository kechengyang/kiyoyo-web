01 / DECISION

三条路线比较：推荐“定制核心，保留平台适配口”

KIYOYO 同时具有现制饮品、门店核销、外送、普通商品、积分和 IP 收藏。业务差异已经超过普通模板商城，但还不需要大规模分布式系统。

OPTION A · FASTEST

全托管商城

以 Shopify 等平台为商品、购物车与订单核心，再额外开发饮品服务。

  • 普通商品上线快、运营工具成熟
  • 饮品与会员逻辑需要大量桥接
  • 双订单/双后台风险较高
  • 平台规则与费用形成约束
OPTION B · BEST FIT

Headless 定制核心

自建 KIYOYO 统一商业核心，第三方支付、短信、地图、配送采用适配器接入。

  • 饮品与商品共享用户、优惠和支付
  • 门店核销与 IP 玩法自然扩展
  • 一个后台、一个订单真相来源
  • 需要稳定的产品与工程团队
OPTION C · TOO EARLY

微服务电商平台

用户、商品、订单、支付、积分等分别部署与治理。

  • 独立扩缩容与故障隔离强
  • 分布式事务与排障复杂
  • 交付和运维成本显著增加
  • 当前规模收益不覆盖成本
建议：以 Option B 启动；为商品平台、支付、配送、消息服务定义适配器接口。如果未来 IP 商品扩张到跨境、多仓或复杂税务，可以只替换“商品电商能力”，不重写 KIYOYO 客户端和会员体系。

为什么不让 App 直接连数据库？

交易规则会分散在各个平台，容易出现 Web 与 App 价格不同、越权访问或旧版本客户端破坏数据。

为什么 MVP 不上 API Gateway？

Firebase Hosting 可把 /api 请求重写到 Cloud Run；应用内完成鉴权、限流与版本控制，减少一个计费与运维层。

03 / GCP LOW-OPS

最省钱的 GCP 方案：只保留一个常驻成本——数据库

候选区域价格层对 Nairobi 的判断决策
Johannesburg · africa-south1Cloud Run Tier 1非洲区、数据路径最直观；Cloud Run 与 Cloud SQL 均可用。暂定首选，必须实测 Safaricom / Airtel / 门店 Wi‑Fi。
Doha · me-central1Cloud Run Tier 1价格层与 Johannesburg 相同，实际线路可能对部分 Kenyan ISP 有优势。作为中东候选，用同配置比较 P50/P95。
Belgium · europe-west1Cloud Run Tier 1产品覆盖成熟，Cloud SQL 可能有不同报价；但更远不等于用户线路一定更慢或更快。作为欧洲候选，不凭猜测直接选。
区域选择门槛：在三个区域各部署同一个轻量 Cloud Run 测试端点，从六家门店和 Kenya 两个主要移动网络采样 48 小时；比较 P50/P95 响应时间、失败率与同规格 Cloud SQL 月价。若成本差异小于约 20%，优先选择延迟更低且波动更小的区域。

预算不是硬上限

04 / NAIROBI STORES

六店最近门店选择：大多数请求不调用 Google Maps

门店是 KIYOYO 自己已知的数据，不需要 Places Nearby Search。设备定位得到用户坐标后，应用对六个门店坐标使用 Haversine 公式排序；只有用户查看地图、地址或导航路线时才调用 Google Maps。

1请求定位Web 用 HTML5 Geolocation；App 用 iOS / Android 系统定位。拒绝时继续手选。
2读取六店坐标store 表保存 lat/lng、营业时间、门店状态、自取/外送能力。
3本地距离排序Haversine 计算直线距离，零 Maps API 调用；默认最近但允许切换。
4服务端校验下单时确认门店营业、菜单可售和履约能力，客户端选择不能越过规则。
5按需地图/路线打开地图才加载 Dynamic Map；确认门店后需要 ETA 才调用 Routes。
当前免费用量参考

Google Maps Web Dynamic Maps 与常用 Essentials SKU 当前各有月度免费用量；但免费额度按 SKU 计算，必须设置每日配额与账单告警。

API Key 安全

Web、iOS、Android 和服务端使用不同 Key；分别限制域名、应用签名、Bundle ID 和允许的 API，禁止把服务端 Key 放进客户端。

05 / STACK

推荐技术栈：主流、可招聘、可替换

选型原则不是追逐最多工具，而是降低跨 Web、移动端和服务端的认知切换，同时守住交易系统的可靠性。

层级推荐为什么适合 KIYOYO替换边界
Web 商城Next.js 静态/预渲染 + Firebase Hosting优先输出可缓存页面，避免为低流量页面持续运行 SSR 服务；需要实时内容时调用 API。SEO 确实需要动态 SSR 时再单独上 Cloud Run。
iOS / AndroidExpo + React Native + Expo Router两端共享大部分页面与业务逻辑；原生推送、相机、深链接和应用商店发布路径清晰。保留平台专属组件目录。
管理后台Next.js 静态站 + Firebase Hosting电脑管理订单，手机完成扫码核销；无须单独发布店员 App。与顾客端分站点、共享组件库。
业务 APINestJS + Cloud Run + REST/OpenAPI一个容器、自动扩缩、request-based billing；TypeScript 全栈。API 契约版本化，未来可按热点拆服务。
交易数据库Cloud SQL for PostgreSQL订单、Mock 支付、积分和六店配置需要事务、一致性、约束与可靠查询。API 与数据库同区；先单区，达到业务门槛后升 HA。
异步任务Cloud Tasks + Outbox通知、重试和超时任务按量触发 Cloud Run，不养常驻 Worker。事件消费者增长后再评估 Pub/Sub。
身份与密钥Identity Platform + Secret ManagerEmail/Social 登录低运维；密钥不进入代码或客户端。Phone OTP 仅在业务证明需要时启用。
代码仓库TypeScript Monorepo共享设计 Tokens、类型、API SDK、校验规则与测试工具，不强行共享所有 UI。apps 与 packages 明确依赖方向。
06 / ORDER DATA

订单模型的关键：支付与履约分离

一个父订单对应一次支付；每个履约组独立拥有门店/地址、时效、状态和操作记录。这样混合购物车、多门店与未来发货能力都能自然扩展。

Order · 父订单

  • order_number / user / channel
  • 商品与价格快照
  • subtotal / discount / tax / total
  • payment_status / currency
  • coupon / points / invoice
1 → N

Fulfillment A · 饮品自取

  • store_id / pickup_code / ready_at
  • PREPARING → READY → REDEEMED

Fulfillment B · 商品配送

  • address_snapshot / carrier / tracking
  • CONFIRMED → SHIPPED → DELIVERED
Mock 支付也走正式接口

PaymentProvider 定义 create / confirm / fail / refund；MVP 的 Mock 实现写入 provider=MOCK，未来替换真实 Provider 不改订单模型。

积分必须是账本

用 earn / spend / expire / reverse 记录变化，不允许直接覆盖余额。余额是账本汇总的结果。

07 / STATES

每类履约都有自己的状态机

状态只能沿允许的路径变化，所有变化记录操作者、时间和原因。Mock 支付确认、核销完成等关键动作同样具备幂等保护，保证未来接真实支付时不用重写流程。

08 / QR REDEMPTION

二维码是“一次性权限”，不是订单信息的明文

二维码只承载高熵随机凭证或短期签名令牌。店员扫码后由服务端校验，任何客户端展示都不能自行决定核销成功。

Pickup #A0188KIYOYO Nairobi Store #1 · READY
1 服务端签发

支付成功并进入自取履约后才生成；二维码不暴露连续订单 ID。

2 门店与状态校验

只允许所属门店核销 READY 状态订单；错误门店明确拒绝。

3 原子化一次核销

数据库条件更新保证两个员工同时扫描也只有一次成功。

4 完整审计

记录订单、店员、门店、设备、时间、结果和异常原因。

5 备用取餐码

相机或屏幕故障时可手输短码，但同样经过服务端验证与限流。

6 最少权限

店员只能核销所属门店，不可查看无关用户信息或任意修改订单。

09 / RELIABILITY

交易同步完成，通知与积分可靠异步

下单接口只承诺“订单与 Mock 支付结果可靠落库”。通知、积分等通过事务 Outbox 与 Cloud Tasks 处理，即使外部服务短暂失败，也能重试而不重复记账。

TRANSACTION订单与支付落库同一事务写入订单、支付记录和待发布事件。
→
OUTBOX / CLOUD TASKS可靠提交任务order.paid · pickup.ready · order.redeemed
→
CLOUD RUN通知 / 积分 / 重试幂等处理，失败由 Tasks 重试，不维持常驻 Worker。
幂等键下单、支付、退款、核销与事件消费都防重复。
Webhook 签名只接受可信支付/配送方回调，并防重放。
可观测性日志、指标、链路与业务告警关联订单号。
备份恢复自动备份并定期演练恢复，不把备份等同于可恢复。
10 / SECURITY

安全与权限从 MVP 开始，不作为“后续优化”

商城处理身份、地址、支付状态、积分和后台权限。设计基线应覆盖 OWASP API 风险，尤其是对象级越权、认证、敏感业务流滥用和第三方 API 消费。

风险MVP 控制经营影响
越权查看/操作订单每次请求校验 user_id / store_id / role；后台按角色与门店授权。防止用户隐私泄露与店员跨店操作。
优惠券、积分、核销滥用服务端规则、限流、一次性令牌、账本与审计。直接保护毛利与会员资产。
重复扣款或重复下单幂等键、支付状态机、Webhook 签名与重放保护。降低客服、退款与对账成本。
敏感数据泄露传输/存储加密、密钥托管、日志脱敏、最少采集与保留策略。降低合规和品牌风险。
第三方服务故障超时、重试、熔断、队列、人工补偿入口与可替换适配器。支付/短信/配送故障不拖垮整个商城。
